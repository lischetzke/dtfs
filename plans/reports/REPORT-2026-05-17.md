## TL;DR — verdict

> **Not ready for "actual test deployment" in the sense the plan promised.**
>
> The cluster *can* be brought up, *a* manager runs, data nodes register, and files can be written through FUSE at ~250 MB/s. But under the surface, **none of the core durability promises hold**:
>
> - **No HA on managers** — the three "manager" VMs are three isolated single-voter Raft instances; there's no code path to add Raft members (F-009).
> - **No replication** — RF=3 is configured, but every chunk lands on exactly one data node. The "3 copies" claim is unimplemented (F-010).
> - **Silent data loss on partial outage** — chunks are assigned to nodes already marked `Down`, the write fails, and the file appears in `ls` with cached content but is zero bytes in the cluster (F-012 + F-013).
> - **Reads are 50× slower than writes** (5 MB/s vs 252 MB/s — F-011).
> - **Self-healing is best-effort and stalls** — re-replication is scheduled correctly when a node fails (real, working code path!) but the scheduler retries the failed source forever instead of picking a fresh replica after recovery (F-015). Under-replication is also never noticed proactively (F-016).
>
> Almost every test the plan asked for — resiliency, self-repair, balancing, hot/cold migration, node failure — touches at least one of the broken pieces. The integration scripts in `tests/integration/` could be made to *pass syntactically* but their results wouldn't mean anything.
>
> The good news amid this: the surrounding pieces ARE real. Build script works on fresh Debian 13, the `deploy/configs/` examples are accurate, data nodes register and heartbeat, failure detection fires at the expected 30 s, the re-replication scheduler exists and emits sensible decisions when it triggers. The cluster has good bones — but the bones are connected to a torso that doesn't yet hold replicas correctly.
>
> **Effort to get to a state where the planned test campaign is meaningful**: ~3–4 weeks of focused engineering. F-009 (multi-manager join), F-010 + F-012 + F-013 (the replication trio), F-015 + F-016 (self-healing actually heals) are the load-bearing fixes. F-003, F-005, F-011, F-014 are smaller follow-ons.

## What actually worked (the green column)

- Rust build on a fresh Debian 13 VM (`scripts/build-linux-amd64.sh`). Rust 1.95.0 stable; the ICE workaround flags from the build script appear to be no-ops on 1.95.
- Cloud-init template + clone-and-configure VMs entirely via Proxmox REST API (no host SSH needed beyond initial key install).
- Manager (single-node) starts cleanly with a config matching the real schema.
- Data nodes register with the manager (`/api/v1/nodes` returns 4 healthy entries with correct location/rack metadata).
- Volume creation via `POST /api/v1/volumes` returns `status: created`.
- FUSE mount works once the systemd unit is patched (F-004 + F-005).
- End-to-end **write path is fast and correct**: 245 MB MKV written in <1 s, md5 matches source on read-back. Chunk count, file size, and used_capacity all line up with the source.
- **Failure detection** fires within the configured window (~30 s for `down_after_missed=6 × 5 s heartbeat`). The node's `health` flips to `"Down"` in `/api/v1/nodes` correctly.
- **Re-replication scheduler is real code**: when a chunk drops below RF, the manager emits log lines like `Auto-scheduled re-replication (replica count 1 < 3)` and transitions tasks through `Pending → Copying`. The state-machine is wired correctly; only the retry logic (F-015) and trigger conditions (F-016) need work.
- The repo's `deploy/configs/mgr-1.toml` and `data-1.toml` ARE accurate examples of the real schema. They were the single most useful artifact for getting past F-003.

So: the **chunks of a working filesystem are all here**. Build, config, registration, failure detection, scheduling — all real. The gaps are in the parts that connect them into a durable replicated whole.

## Recommended next steps (priority order)

1. **F-010 first** (durability is the product). Make `PlacementEngine::allocate_chunks` return N target nodes for a chunk, have the FUSE write-coordinator issue parallel writes to all of them and only ACK when `min_replicas_before_ack` succeed. Without this, "DTFS" is a slow single-disk filesystem with a manager service in front.
2. **F-012 + F-013 in the same patch.** Filter `Down` nodes out of placement and make FUSE flush surface the underlying write error. These are short fixes that prevent silent data loss.
3. **F-009.** Multi-manager Raft join. The cleanest path is option (3) in F-009: `initial_voters` in `manager.toml` so a 3-node Raft initialises atomically. After this, F-015 retries become testable end-to-end (with a real Raft replica set, the "fixed source forever" bug exposes itself in more scenarios — and is easier to fix because there's now a leader to consult).
4. **F-015 + F-016 together** — re-replication retry logic and proactive under-replication scan. These are real code paths today, but stop short of being self-healing.
5. **F-011 (read perf).** Profile the read path; 50× regression is likely a single bottleneck (single-RPC-per-chunk or no readahead).
6. **F-003.** Regenerate Ansible templates from `deploy/configs/*.toml` examples — or delete the stack entirely. Right now it confidently produces a non-working deployment.
7. **F-005 + F-004.** Trivial systemd unit fixes.
8. **F-006 + F-014.** Capacity and timestamp plumbing — small, isolated, useful.
9. **Then re-run this campaign.** Once the above are in, the integration scripts in `tests/integration/` and the chaos tests in `tests/chaos/` should produce signal worth reading. I'd expect a second wave of findings (partition-safety FUSE wiring, sequential re-replication throughput under load, tiering with non-zero capacity, etc.), but they'll be *real* findings about real behaviour rather than "this layer isn't connected to that layer."
