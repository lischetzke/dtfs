## Finding 1: cluster has no Raft leader for >2 h and cannot elect

- Severity: critical
- Area: raft
- Evidence:
  - `GET mgr02:/api/v1/raft/state`: `"state":"Candidate","current_term":1183,"current_leader":null,"vote_committed":false` (votes for itself).
  - `GET mgr03:/api/v1/raft/state`: `"state":"Candidate","current_term":877` — terms diverged ⇒ zero successful vote exchanges between the two healthy voters.
  - mgr02 journal, continuous since 20:53:02Z, ~1.5 elections/s:
    `ERROR openraft::core::raft_core: timeout: timeout after 400ms when Vote 4949484375257702517->1028174117865612657` (and `->16102692085452801416`).
  - TCP is NOT the problem: from mgr02, `mgr03:9401 OPEN` (and vice versa); only `mgr01:9401 FAIL`.
- Expected: with mgr01 dead, mgr02+mgr03 = 2/3 voters elect a leader within seconds.
- Actual: mutual vote-RPC timeouts (400 ms budget) for >80 min; election deadlock.
- Hypothesis: each survivor's raft core is starved — mgr03 by the monitor spin (Finding 3, 2424 log-lines/min + 1920-task state scans + failing raft writes), mgr02 by the cluster-wide RegisterNode retry storm + its own election churn — so inbound Vote RPCs queue >400 ms. The 400 ms vote timeout is tight for loaded 1–2 vCPU VMs and leaves no headroom. Needs investigation in openraft config + the flood sources.
- Suggested next step: emergency recovery ordering for the operator (restart mgr03's manager to kill the spin → mgr02+mgr03 elect → then restart wedged mgr01 + fsn-mgr01). Then code fixes per Finding 3 + consider raising vote/election RPC timeouts. NOTE: 36k tasks are persisted in the state machine (Finding 5) — dispatch resumes on the new leader and may re-trigger the storm; triage should plan task purge/gating BEFORE or together with restarts.

## Finding 3 (root cause): monitor::handle_node_down runaway — unguarded, mis-targeted re-replication storm

- Severity: critical
- Area: migration / replication
- Evidence:
  - mgr03 journal, every ~40 s since ~21:19Z, still firing at sweep time:
    `WARN dtfs_manager::monitor: Node 3153314871633689230 is DOWN -- triggering re-replication check`
    `INFO dtfs_manager::monitor: Scheduled 1920 re-replication tasks for chunks on down node 3153314871633689230`
    Rate check: 2424 `Scheduled replication task` lines in the last 60 s.
  - Task id frozen: every scheduled task logs `task_id=repl-17021` (`next_task_id` never persists — every `save_migration_state` fails: `Bug AB save_migration_state failed: has to forward request to: None, None (may not be leader)`).
  - Targets cycle ALL registered nodes incl. managers and the FUSE client, and even source==target:
    `task_id=repl-17021 chunk=83d95e... source=8412905743711879271 target=8412905743711879271`; other passes target `1028...`/`4949...`/`16102...` (managers), `12017...` (client `dtfs-lm-data01_cln`).
  - `GET mgr02:/api/v1/migrations`: `"count":36162` persisted tasks. Audit log is a wall of `migration.failed` / `result: ReplicateChunk error: ... Chunk not found: <id> attempts=6` — source node picked was fsn-data01, which holds only 414 of the 4135 chunks (deep scrub 19:37Z: `checked=414`), so most evacuation tasks name a source that doesn't have the chunk.
  - Code (origin/master = deployed wave), `crates/dtfs-manager/src/monitor.rs::handle_node_down`:
    1. NOT leader-gated — Bug AC gated `scheduler::tick()` only; the monitor runs on every manager and calls `scheduler.schedule_replication(...)` directly.
    2. `healthy_nodes` filter is `id != down && health == Healthy` — no `role == Data` filter, so managers/clients become replication targets.
    3. `DiskTier::Hot` hardcoded — the cluster has only cold+warm disks; volume `default` has hot disabled (`cache hot max 0`, `spill.forbidden_tiers: ["hot","tape"]`).
    4. No source-holds-chunk verification beyond "another replica entry exists in metadata" and no dedup against in-flight tasks → 1920 fresh tasks per 40 s pass, forever.
- Expected: node-down repair runs only on the leader, targets healthy DATA nodes on a valid tier, schedules each missing replica once.
- Actual: while mgr01 still led, each mgr03 monitor pass forwarded ~1920 garbage tasks into the leader's raft (~23 passes ≈ the 36–40k observed) until the leader OOM-wedged; after leader loss the same loop spins locally, starving mgr03's raft core (→ Finding 1).
- Hypothesis: confirmed from code + logs (above). The Down flap itself was real-but-transient: lm-data01's dtfs-data pinned at its 2.2G memory cap during the warm backfill dispatch storm and missed heartbeats (Finding 4).
- Suggested next step: new bug plan (next free letter — CG is informally claimed by the Minicluster silent-truncation candidate; suggest **BUG-CH**): leader-gate the monitor, role-filter targets to healthy Data nodes, derive tier from volume policy instead of hardcoded Hot, verify source holds the chunk, dedup against existing/in-flight tasks, and bound tasks-per-tick. Plus an op-path to purge the 36k poisoned tasks from migration state.
