## Finding 1: Entire library is single-homed on one cold disk — configured warm replica is never created

- Severity: **critical**
- Area: replication
- Evidence:
  - `GET /api/v1/volumes/default`: `"replication":{"cold":1,"warm":1,...}`,
    `"mandatory_replicas":{"cold":1,"warm":0,...}`,
    `"cache_replicas":{"warm":{"min":1,"max":1},"per_dc":true,"promote_reads":0,"promote_window_secs":0,"cooldown_secs":0}`.
  - Full-volume chunk scan via `/api/v1/files/inspect` (102 committed files):
    `total_chunks=41230 cold_replica_chunks=41230 warm_replica_chunks=132`,
    `files_with_zero_warm=101`, warm coverage **0.32%**.
  - `GET /api/v1/nodes`: dc1 warm disk `used_bytes=1744175104` (1.74 GB),
    **frozen across the whole sweep** (lifetime `total_bytes_written=1730131547`,
    `total_bytes_read=0`) while prod-data01 cold grew 214 -> 221 GB live.
  - `GET /api/v1/stats`: `chunk_placement {stable:41823, undergoal:0, missing:0}`
    — the scheduler believes placement is complete.
  - Capacity cross-check: used ~216 GB ≈ logical 172 GB × RF 1 (+ ~25% 4 MiB
    chunk-padding/meta overhead), not the ~344 GB RF=2 would need.
- Expected: every chunk gets 1 cold (anchor) + 1 warm replica per
  `replication.warm=1` / `cache_replicas.warm.min=1`.
- Actual: 101/102 files are cold-only. One disk (prod-data01 /mnt/hdd0) holds the
  only copy of ~172 GB. Disk loss = total library loss. `undergoal:0` and
  `files_missing_chunks:0` mask the gap (both count mandatory only).
- Hypothesis: config-authoring/engine mismatch. Warm is configured as a *cache*
  replica (mandatory warm=0), and per the AV invariant (AGENTS.md § A.3.4) only
  the tiering engine creates cache replicas, gated on `promote_reads` /
  `promote_window_secs` — both 0, so promotion can never fire (and dc1 has
  lifetime reads = 0 anyway). The under-replication scheduler is forbidden from
  backfilling cache replicas. So `cache_replicas.warm.min=1` is inert as
  authored, and `replication.warm=1` appears to have no maintainer. The 132
  warm chunks (1.7 GB ≈ 414 × 4 MiB) are residue of one early bootstrap wave
  (see Finding 7). Violates A.3.3 #5 (never silently downgrade RF).
- Suggested next step (triage): decide intent. Durable second copy =>
  `mandatory_replicas.warm=1` (scheduler then maintains it). Demand cache =>
  set non-zero `promote_reads`/`promote_window_secs`. Separately scope a code
  question: should a `cache_replicas.min > 0` floor be maintained independently
  of promotion, and should `replication.warm` with no mandatory/cache maintainer
  be rejected or surfaced as under-replication instead of `undergoal:0`?

## Finding 2: dc1 manager never joined the raft cluster (user's reported symptom)

- Severity: **high** (root cause of reported issue)
- Area: raft | config
- Evidence:
  - dc1 `GET /api/v1/raft/state` (re-verified 15:49):
    `"state":"Learner","current_term":0,"last_log_index":0,"voters":[],"current_leader":null,"node_id":"10416916305544135812","hostname":"dtfs-dc1-mgr01"`.
  - Leader voters: `["1028174117865612657","4949484375257702517","16102692085452801416"]`
    (the 3 prod-mgrs) — dc1's node_id absent on all three prod views.
  - dc1 `/cluster/status`: `data_nodes:0, files:0, total_capacity:0` — serves
    its own empty state machine. Hence "sees no client, incomplete manager info".
  - `/etc/dtfs/manager.toml` on dc1 (re-verified): `[node] hostname = "dtfs-dc1-mgr01"`
    while machine hostname is `dtfs-dc1-data01`, and the configs' 4th
    `[[cluster.initial_voters]]` entry is `{hostname:"dtfs-dc1-data01", addr:"100.64.0.10:9401"}`
    on ALL four managers. dc1 journal: `WARN Bug AC bootstrap: no matching
    initial_voters entry for self; falling back to grpc.listen_addr`.
  - Leader audit (428 rows, full uptime): zero join/add-learner/membership rows
    for dc1 — never invited from the leader side.
  - Network exonerated: TCP probes from dc1 to prod 9401/9402 all OK; tailscale
    peers active.
- Expected: dc1 manager joins the 3-voter cluster (learner -> voter) and
  replicates the real log.
- Actual: identity self-match fails (advertised hostname `dtfs-dc1-mgr01` is
  not in `initial_voters`, which says `dtfs-dc1-data01`), no leader-side
  add-learner was ever issued, so it idles as an inert empty term-0 learner.
- Hypothesis: manager.toml cloned from an "mgr01" template — `[node] hostname`
  (and `[location] host = "mgr01"`) never updated; auto-join therefore never
  matched, and the manual membership-change step was never run.
- Suggested next step (triage; mutations): CORRECTION after code review — the
  codebase has NO add-learner/change-membership path (the only membership
  mechanism is `raft.initialize()` on the bootstrap node; `/api/v1/join/*` is
  the data-node handshake, not raft membership). Fix direction: change the 4th
  `initial_voters` entry to `dtfs-dc1-mgr01` on all 4 managers (do NOT rename
  the dc1 manager to `dtfs-dc1-data01` — that collides with the data daemon's
  node_id, both being hash(hostname)). Then growing the voter set requires a
  planned re-initialization of the raft group (backup, wipe, re-bootstrap with
  the 4-entry voter list — see docs/src/operations/cluster-management.md), or
  implementing an online add-learner flow first.

## Finding 4: Manager delete fan-out to prod-data01:9500 failing continuously — orphan chunks leaking during active ingest

- Severity: **high**
- Area: node | integrity (space)
- Evidence (coordinator-verified 15:48-15:50 CEST):
  - mgr01 journal: 61 total `WARN dtfs_manager::metadata: Bug N delete fan-out:
    connect failed, leaving orphan chunks for reconciler ...
    node_addr=http://100.64.0.20:9500 error=transport error` since first
    occurrence 12:49:47 UTC; 44 in the last 45 min; **4 in the last 5 min** —
    active, one per `.filepart` unlink of the ongoing ingest.
  - Yet: `ss -tlnp` on prod-data01 shows `dtfs-data` LISTENING on
    `100.64.0.20:9500`, and a raw TCP probe from mgr01 to 100.64.0.20:9500
    succeeds (`MGR_TO_DATA01_9500_OK`). dc1's data node successfully replicates
    chunks to the same `http://100.64.0.20:9500`, and FUSE I/O on prod-data01 is
    healthy.
- Expected: manager unlink fan-out deletes chunks on the data node; orphans only
  on crash windows (A.6 #8).
- Actual: every delete fan-out from the manager to prod-data01 fails at the gRPC
  layer while TCP connects fine and other gRPC clients reach the same port.
  Orphan chunks accumulate on the cold disk for every replaced `.filepart`
  during ingest; reclamation now depends entirely on the orphan reaper/scrub
  (Bug CB grace, measured against on-disk mtime).
- Hypothesis: gRPC-level mismatch specific to the manager's delete-fanout
  client — candidates: TLS `mode="auto"` asymmetry (manager dials plaintext
  h2c; both ends log TLS-auto-not-implemented warnings, so possibly a
  half-implemented handshake on this path), a stale/cached broken channel from
  the 13:33 data-node restart window, or an overly tight connect timeout under
  ingest load. Unknown — needs code/trace investigation.
- Suggested next step (triage): reproduce with verbose gRPC logging on the
  manager delete path; check whether the fan-out client reuses a channel created
  while the data node was down (13:28-13:33 restart window) and never re-dials;
  quantify orphaned bytes on /mnt/hdd0 (scrub orphan pass) and confirm the
  reaper drains them once connectivity is fixed.

## Finding 5: write_safety.min_replicas_before_ack=2 is not durably satisfiable — ack guarantee likely degraded

- Severity: **high**
- Area: replication
- Evidence: `volumes/default`: `"write_safety":{"min_replicas_before_ack":2,...}`.
  Topology: exactly one cold disk + one warm disk. Per Finding 1 the warm
  replica is never (now) placed, yet ingest is acking and completing
  (files 110 -> 112 during sweep; chunk_placement.stable +663 in 120 s).
- Expected: no ack until 2 replicas durable; durable state keeps 2 replicas.
- Actual: steady state is 1 replica. Either the ack counts a transient/wrong
  replica or the floor is silently degraded to 1; with dc1 down, writes might
  instead block to timeout.
- Hypothesis: ack accounting counts the (formerly produced) warm staging copy
  or is not enforcing 2 distinct durable replicas. Unknown — needs code trace
  of put ack vs `min_replicas_before_ack`.
- Suggested next step (triage): trace the put/commit ack path against this
  setting; reconcile with Finding 1's resolution (mandatory warm=1 would make
  ack=2 honest).
