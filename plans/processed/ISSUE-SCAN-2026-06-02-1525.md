## Finding 1: Peer-manager version/build_date blank in WebUI — managers don't publish version to shared state

- Severity: low
- Area: raft / api / webui
- Evidence:
  - `GET /api/v1/nodes` against each manager shows only the *serving* manager's
    own version; the other two are blank:
    - via mgr01 (`10.150.0.171:9402`): `mini-mgr01` has
      `version:"v0.0.0-dev"`, `build_date:"20260522-131629"`; `mini-mgr02` and
      `mini-mgr03` have neither field.
    - via mgr02 (`10.150.0.172:9402`): only `mini-mgr02` is versioned.
    - via mgr03 (`10.150.0.173:9402`): only `mini-mgr03` is versioned.
    Data/client nodes (mini-data01/02, mini-client01) carry version on every
    manager — they register through `RegisterNode`.
  - Code, `crates/dtfs-manager/src/api.rs:778-792`:
    ```
    // Bug AY — managers don't go through RegisterNode, so the only
    // version we can confidently fill is the local manager's own
    // (the one serving this API call). Other managers' version
    // stays empty until a future per-manager status RPC is wired.
    let is_local = v.hostname == state.config.node.hostname;
    let synth_version = if is_local { VERSION.to_string() } else { String::new() };
    ```
  - WebUI render is correct and not at fault:
    `crates/dtfs-manager/src/webui.rs:1045` / `:1543` build the version cell as
    `n.version || '—'` — they display `—` when the field is empty. The blank is
    the data, not the markup.
- Expected: the WebUI node table shows a version + build_date for every manager,
  regardless of which manager serves the page.
- Actual: only the manager that served the request shows its version; the other
  managers render `—`. Whichever manager the operator points the WebUI at, the
  other two look version-less.
- Hypothesis: managers are Raft peers, not nodes that call `RegisterNode`
  against the leader, so their `version`/`build_date` never land in the shared
  state-machine node registry. The API synthesizes the local manager's version
  from `dtfs_common::version::{VERSION,BUILD_DATE}` but has no source for peer
  managers. This is the documented Bug AY gap; it persisted across scans
  (2026-05-28 noted "mgr02 missing version/build_date").
- Suggested next step: wire managers to publish their own `version`/`build_date`
  into shared Raft state so any manager's API/WebUI can report all peers. Options
  for triage: (a) each manager self-registers via the existing `RegisterNode`
  path on startup (role=manager) — version flows through
  `metadata.rs:565` into the registry like data nodes; (b) carry
  version/build_date in a per-manager status/membership field gossiped via Raft.
  Option (a) reuses an existing, audit-idempotent path (Bug BJ
  `node_info_material_eq` already treats version as a material field) and is the
  smaller change. Coordinate with the same per-manager liveness gap noted at
  `api.rs:805` (peer `last_seen_ms` is synthesized as now), which a manager
  self-register/heartbeat would also fix.

## Summary

- low: 1 (peer-manager version/build_date blank in WebUI — managers don't
  publish version to shared Raft state; UI renders the empty value as `—`)

Not a WebUI rendering bug. The node table correctly shows `—` for an empty
version; the gap is upstream — managers never write their `version`/`build_date`
into the shared node registry, so each manager only knows its own. Fixing it
(manager self-registration via `RegisterNode`, or per-manager status in Raft)
would also close the related synthesized-`last_seen` gap for peer managers.

Hand to triage session for planning. Candidate new bug letter (BR), or fold into
a manager-self-registration plan alongside the client-heartbeat finding
(ISSUE-SCAN-2026-06-02-1512, candidate BQ) — both are the same root shape: a
node class that never self-registers/heartbeats into shared state.
