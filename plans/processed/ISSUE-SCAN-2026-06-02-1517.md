## Finding 1: data01 both disks 100% full — 0 bytes available

- Severity: critical
- Area: disk
- Evidence:
  - `ssh debian@10.20.0.174 df -h /mnt/data01-warm /mnt/data01-cold`:
    ```
    Filesystem  Size  Used Avail Use%  Mounted on
    /dev/sda     20G   19G     0 100%  /mnt/data01-warm
    /dev/sdb     20G   19G     0 100%  /mnt/data01-cold
    ```
  - `/api/v1/nodes` data01 disks: warm `used_bytes:19866927104` /
    `total_bytes:20957446144` = 94.8% per API (OS-level df shows 100%,
    suggesting reserved blocks are exhausted too).
  - `find /mnt/data01-warm/chunks /mnt/data01-cold/chunks -name '*.dat' | wc -l`
    = 314 chunk files total (~1.25GB at 4MB/chunk).
  - `find /mnt/data01-warm/tmp /mnt/data01-cold/tmp -name '*.tmp' | wc -l` = 84
    streaming temp files. With 19GB on each disk and only ~1.25GB in committed
    chunks, the 84 temp files account for the bulk (~18.5GB / 84 ≈ 220MB avg).
  - `GET /api/v1/stats`: `io_write_bytes_per_sec:97760839` (~93MB/s) — active
    writes in progress at sweep time. New writes are presumably landing on data02
    (only 2.1MB used) since data01 is full; the temp files are from earlier
    in-flight transfers that filled data01 before completing or failing.
- Expected: data disks have headroom for incoming data plus temp files; the
  `commit_chunk_from_tmp` path should clean up tmp files on any error.
- Actual: both disks at 100% (0 bytes free). 84 temp files (~18.5GB) consuming
  nearly all disk space; only 314 committed chunk `.dat` files (~1.25GB).
- Hypothesis: streaming transfers wrote large temp files to data01, filling the
  disks. If commits failed mid-transfer (disk filled after temp write started),
  the cleanup path may not have run, leaving the tmp files in place. The 84
  lingering `.tmp` files strongly suggest a cleanup bug — either `commit_chunk_from_tmp`
  error paths are not removing the tmp on failure, or a crash during transfer
  left them orphaned (WAL recovery should handle this on restart but may not
  have run yet). Also possible the transfer simply hasn't finished and the
  `.tmp` files are live in-progress writes — but at 100% full, they cannot
  complete.
- Suggested next step: triage scope (a) verifying whether these 84 `.tmp` files
  are orphaned (no corresponding active write lease) or genuinely in-progress
  (active lease); (b) if orphaned, operator-level cleanup to free space so
  anchor cold replication can proceed; (c) tracing the `commit_chunk_from_tmp`
  error paths to confirm tmp cleanup runs on disk-full conditions.

## Finding 2: Anchor invariant violated — 149 cold-tier anchor tasks stuck "No space left on device" on data01-cold

- Severity: critical
- Area: anchor / migration
- Evidence:
  - `GET /api/v1/migrations`: `count:149`. Migration analysis:
    `total=149, source==target=149, has_error=126, max_attempts=6`.
  - All tasks are `tier:cold`, all `source_node == target_node ==
    9163562228154835649` (mini-data01). Representative error:
    `"create tmp /mnt/data01-cold/tmp/streaming-85063-....dat.tmp: No space
    left on device (os error 28)"`.
  - mgr01 log: `WARN dtfs_manager::scheduler: Copying retry queued
    task_id=anchor-177 chunk=d238a7e2... attempt=5 max=6 reason=... No space
    left on device`.
  - Task `anchor-177` at attempt=5 of max=6 — one more failure and it exhausts
    retries permanently.
  - `GET /api/v1/volumes` `default`: `anchor:{datacenter:"dc-a",
    required_tier:"cold"}`, `mandatory_replicas.cold:1`.
  - data02 is in dc-b and cannot satisfy the dc-a anchor requirement.
- Expected: every chunk in the `default` volume has a mandatory cold replica on
  dc-a (data01). The anchor-lag scheduler should successfully place these replicas.
- Actual: data01-cold is 100% full; all 149 cold-tier anchor tasks fail at the
  tmp-write stage. 126 of 149 already carry error records. At least one task
  (anchor-177) is at attempt=5/6 — permanent failure one retry away. Once tasks
  exhaust max=6, the anchor cold replica is never written and the anchor invariant
  is permanently violated for those chunks unless the tasks are re-queued after
  space is freed.
- Hypothesis: the anchor tasks correctly identify data01 as the sole dc-a cold
  node (single dc-a data node topology). The failure is entirely capacity-driven:
  data01-cold is 100% full because of the orphaned `.tmp` files (Finding 1). The
  `source_node == target_node` pattern is expected (BH fix: mandatory cold +
  cache warm on same single-dc-a node), not a bug.
- Suggested next step: linked to Finding 1 — freeing data01-cold space (by
  cleaning orphaned .tmp files) will unblock the anchor tasks. However, tasks
  that have already exhausted max=6 attempts will need to be re-queued. Triage
  should check whether the scheduler auto-requeues exhausted anchor tasks or
  whether they permanently enter a failed state requiring operator intervention.

## Finding 3: ~5.8GB phantom bytes (orphaned chunks)

- Severity: high
- Area: integrity
- Evidence: `GET /api/v1/stats`: `phantom_bytes_estimate:5820624579` = ~5.4GB.
  `logical_bytes:35624228547` = 35.6GB; `raw_used_bytes:39738138624` = ~37GB;
  `net_used_bytes:29803603968` = ~27.8GB. Gap between `raw_used` and
  `net_used` (~9.2GB) includes both phantom (5.4GB) and replication overhead.
- Expected: `phantom_bytes_estimate` near zero after a clean cluster rebuild —
  all on-disk data should correspond to live chunk metadata.
- Actual: 5.4GB of phantom (orphaned) data present immediately after rebuild.
  Combined with the 84 `.tmp` files (~18.5GB in Finding 1), most of data01's
  100%-full disk is data not tied to valid chunk records. Note: the `.tmp` files
  are not counted as orphan chunks (they are not committed chunks), but they
  occupy space that phantom-byte cleanup would not reclaim.
- Hypothesis: the 5.4GB phantom is either (a) residue from the prior data-loss
  cycle that was not fully cleaned, or (b) chunks written during the new ingest
  whose warm→cold replication failed, leaving warm-only copies the metadata
  references as having no cold location. Requires investigation.
- Suggested next step: run an orphan scrub pass (after space is freed to allow
  it to operate) to enumerate and reclaim phantom chunks. Cross-check whether the
  5.4GB overlaps with the `.tmp` disk usage or is independent committed-but-stale
  chunk data.

## Finding 4: Active writes proceeding without anchor cold coverage (writes landing on data02-warm, dc-b only)

- Severity: high
- Area: anchor / replication
- Evidence:
  - `GET /api/v1/stats`: `io_write_bytes_per_sec:97760839` (~93MB/s) at sweep
    time.
  - data01-warm 100% full; data02-warm `used_bytes:2142208` = ~2MB (newly written
    data landing here).
  - 149 anchor tasks pending but failing (Finding 2) — no cold anchor copy for
    any of the 43 active files.
  - `default` volume `write_safety.min_replicas_before_ack:2` — writes ack after
    2 replicas, both ending up on data02 warm (dc-b) since data01 is full.
  - `files_missing_chunks:0` in `/api/v1/cluster/status` — misleading; chunks
    exist on warm but cold anchor copies are absent.
- Expected: each chunk written to the `default` volume gets a cold anchor copy
  on dc-a within the replication window; `min_replicas_before_ack:2` counts
  both mandatory warm and mandatory cold replicas.
- Actual: new writes ack with 2 warm replicas on data02 (dc-b), no cold anchor
  copy (data01-cold full, only dc-a cold node). The anchor invariant is violated
  from the moment of write. If data02 fails before data01-cold is freed and
  anchor tasks catch up, data loss recurs.
- Hypothesis: `min_replicas_before_ack:2` counts warm replicas toward the ack
  threshold, not specifically requiring that one replica satisfies the anchor
  constraint. This is a known write-safety design tension — the ack fires before
  the cold mandatory is placed, relying on the async anchor-lag scheduler to
  converge. With the scheduler blocked (Finding 2), convergence cannot happen.
- Suggested next step: triage should decide whether to halt ingestion until
  data01-cold space is freed and anchor tasks can converge, or accept the risk
  that new data is unprotected during the recovery window. Separately scope
  whether `write_safety` should block ack until the mandatory cold anchor replica
  is also placed (behaviour change, not just config).

## Finding 5: volume config rebuilt with tiering knobs zeroed — cache promotion effectively disabled

- Severity: medium
- Area: volume
- Evidence: `GET /api/v1/volumes` `default`:
  `cache_replicas.cooldown_secs:0`, `promote_reads:0`, `promote_window_secs:0`.
  In sweep 4 (before rebuild): `cooldown_secs:30`, `promote_reads:2`,
  `promote_window_secs:60`. `config_version:0` (fresh rebuild).
- Expected: tiering knobs set to operational values; `promote_reads:0` means the
  read-promotion threshold is zero reads, which may either disable promotion
  entirely or fire on every read (depends on the scheduler's zero-handling).
- Actual: all tiering thresholds reset to zero. This is likely a default
  post-rebuild config that was never tuned back to the previous values.
- Hypothesis: cluster rebuild wiped the previous `config_version:19` volume
  config; the new `default` volume was recreated with default/zero values.
  If `promote_reads:0` means "never promote" (threshold not met by 0 reads),
  the tiering engine is inert — warm→hot promotion won't run, which is
  low-risk for now but will produce unexpected behaviour when playback starts.
- Suggested next step: verify expected semantics of `promote_reads:0` in the
  scheduler code. Restore non-zero tiering config to the previous values if
  the cluster is to resume serving Plex.

## Summary

- critical: 2 (data01 both disks 100% full — 84 orphaned .tmp files ~18.5GB;
  149 anchor tasks all failing "No space" — anchor invariant violated for all 43
  active files)
- high: 2 (5.4GB phantom bytes; active ingestion producing unanchored chunks
  with no cold coverage)
- medium: 1 (tiering knobs reset to zero after rebuild)
- low: 2 (cluster_status data_nodes count bug; stale build_date)

Single root cause links Findings 1 and 2: 84 `.tmp` files (~18.5GB) have filled
data01-warm and data01-cold to 100%, blocking all anchor cold replica writes.
Findings 3 and 4 are downstream: phantom bytes from the tmp/orphan accumulation,
and new writes arriving without anchor coverage because the cold disk has no
room. Freeing data01-cold (by cleaning orphaned .tmp files) is the prerequisite
for unblocking the anchor repair queue.
