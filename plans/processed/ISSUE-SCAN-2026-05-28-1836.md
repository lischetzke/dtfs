## Finding 2: Disk UUIDs regenerated on every data node restart — root cause of data loss

- Severity: **critical**
- Area: disk, node
- Evidence:

  Disk UUIDs observed across three sweeps today (data from `GET /api/v1/nodes`):

  | Node | Disk | Sweep 1 (14:16) | Sweep 2 (17:47) | Sweep 3 (18:36) |
  |------|------|----------------|----------------|----------------|
  | data01 | warm | `cef0063d...` | `bc9b8700...` | `e647e90a...` |
  | data01 | cold | `fa202de8...` | `e48a15d5...` | `2551f55f...` |
  | data02 | warm | `c199eae0...` | `c199eae0...` (unchanged) | `69049503...` |
  | data02 | cold | `78063e5a...` | `78063e5a...` (unchanged) | `da2d770f...` |

  data01 was restarted three times today (pid 71483 → 75875 → 75954 → new pid at 17:51:12). Each restart produced a new UUID set. data02 was stable through sweep 2 then restarted at 17:51:18 — UUID changed.

  From `journalctl -u dtfs-data -n 50` on data01 at each restart:
  ```
  INFO dtfs_data::store: ChunkStore startup rescan complete chunks=28 bytes=109051904
  ```
  Every restart found exactly 28 chunks — the 28 chunks that physically survive disk reprovisioning (or that were written after the previous wipe). Chunks from the OLD UUID set are not rescanned under the new UUID.

  data01 warm disk usage between sweep 2 (108 MB, ~27 chunks) and sweep 3 (17,762 MB, ~4441 chunks): FUSE writes actively added ~4413 chunks after the 17:51 restart — all under the new `e647e90a...` UUID. These new chunks DO have valid Raft location records. The OLD chunks (under `cef0063d` and `bc9b8700` UUIDs) are the ones with no source replica.

- Expected: disk UUIDs are stable persistent identifiers stored on the disk itself (e.g., written to a metadata file under the mount point on first initialization). They must survive service restarts so Raft chunk location records remain valid across process lifecycle events.
- Actual: UUIDs are regenerated on every service start. Raft state retains location records pointing to the old UUIDs. On the next restart, the data node registers with new UUIDs and the old records are orphaned — the cluster no longer knows those chunks exist, and the GC scheduler eventually deletes the physical files as unreferenced orphans. The anchor-lag repair scheduler then tries to reconstruct the mandatory copies but finds no source.
- Hypothesis: the disk UUID is generated with `Uuid::new_v4()` (or equivalent) at startup rather than being loaded from a persistent file on the mount point. This is an initialization path bug: the code that should read an existing `disk.uuid` file likely always overwrites it (or the file is never created). Every restart effectively tells the cluster "these are brand new disks."
- Suggested next step: Triage must investigate the disk initialization code in `dtfs-data` (likely `crates/dtfs-data/src/disk.rs` or similar) to confirm whether UUIDs are persisted to disk or generated fresh each start. Fix must write the UUID to a file on the mount path at first init and read it on subsequent starts. This is the root cause of Finding 1.

- Expected: when a file chunk is written to data01's warm tier, the anchor policy requires a cold replica be placed on data01's cold disk (dc-a/cold). The scheduler should queue an anchor-lag repair task for each new warm chunk that lacks a cold copy.

- Hypothesis: the anchor repair scheduler may be backlogged handling the 121 stuck tasks, delaying detection of the newly written warm-only chunks. Or the new chunks' anchor repair tasks are queued but not yet visible because the 121 are ahead of them in the queue.

## Finding 4: Disk UUID rotation bug also causes each restart to look like a fresh node to the GC scheduler

- Severity: **high**
- Area: disk, replication
- Evidence:

  On each data node restart: `ChunkStore startup rescan complete chunks=28 bytes=109051904`. The rescan scans disk for physical chunk files and builds an in-memory index. The Raft state machine holds location records keyed by `(node_id, disk_uuid)`. After restart, the new UUID means no Raft record matches the physical files — they appear as orphans.

  The previous ~162-chunk deficit (finding from sweep 2 report: ~499 orphan chunks, ~1.95 GB) resolved between sweep 2 and this sweep because the GC orphan-scrub ran and deleted the physical files that were no longer referenced in Raft state. Those files are now permanently gone.

- Expected: orphan GC should only delete files that are genuinely unreferenced. A file on disk that is referenced by Raft state under its correct UUID is NOT an orphan.
- Actual: because UUID rotates, the Raft records reference old UUIDs that no longer exist after restart. The physical files remain temporarily (the GC has a grace period), then are deleted. This explains the complete disappearance of ~330 data01 chunks between sweep 1 and sweep 2: they were GC'd as orphans after the first restart changed the UUID.
- Suggested next step: fixing Finding 2 (stable UUIDs) prevents this. As a safeguard, the GC grace period should be long enough to survive a brief outage + restart. Triage should review the orphan GC grace period (`grace_secs=86400` from scheduler log BF-7) against the current data loss timeline to confirm whether a 24h grace would have prevented the deletions.

## Finding 5: RegisterNode RPC fails on non-leader at startup — data node walks list without reaching leader

- Severity: **high**
- Area: node, raft
- Evidence:

  From `journalctl -u dtfs-data -n 50` on data01 at 17:52:04-17:52:05:
  ```
  WARN dtfs_data: RegisterNode RPC failed: status: Unavailable, message: "manager is not the leader: has to forward request to: Some(933575918632954229), Some(DtfsNode { addr: \"10.150.0.173:9401\", hostname: \"mini-mgr03\" })"
  INFO dtfs_data: Switched to manager at http://10.150.0.172:9401
  WARN dtfs_data: RegisterNode RPC failed: [same message, redirecting to mini-mgr03]
  ```
  Data node attempted mgr01 (non-leader), then mgr02 (non-leader), both returned "not the leader." Did not connect directly to mini-mgr03 (the actual leader).

- Expected: when a manager returns "not the leader, forward to X" for a RegisterNode RPC, the data node should immediately retry against the provided leader address (mini-mgr03 at `10.150.0.173:9401`), not walk to the next sequential entry in the manager list.
- Actual: data node walks the manager list sequentially. mgr01 → mgr02 → (presumably mgr03 eventually). This means registration takes 2+ extra round trips and relies on eventually walking to the leader by position, not by hint. If the leader is the last entry, startup takes 3× longer than necessary. If the list is long and the leader is unlucky, more failures accumulate.
- Hypothesis: the reconnect/register client code reads the "forward to" address from the error but ignores it, using a sequential-walk fallback instead. The hint is embedded in the gRPC error but the client code discards it.
- Suggested next step: Triage should check the RegisterNode client path in `dtfs-data` — the error contains the leader's address. The fix is to parse it and retry directly rather than walking sequentially. This applies to both RegisterNode (startup) and Heartbeat (ongoing) — both suffer from the same sequential walk problem (Finding 7 from prior scans).
