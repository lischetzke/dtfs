## Finding 1: Raft storage exhausted on managers — mgr01 raft node Shutdown, leader mgr03 at 98%

- Severity: critical
- Area: raft
- Evidence:
  - `GET /api/v1/raft/state` (from mgr01): `"state":"Shutdown"`,
    `"running_state":"fatal: when Write Log(... index: 2380332): IO error: No
    space left on device: While appending to file:
    /var/lib/dtfs/manager/raft-log/4496458.sst: No space left on device"`,
    `current_leader":"933575918632954229"` (mgr03), `current_term":114112`,
    `voters":["933575918632954229","10246119977476202431","11864861879977870146"]`.
  - `ssh debian@10.150.0.171 df -h /var/lib/dtfs`:
    `/dev/sda1 16G 15G 160M 99% /`; `du -sh raft-log` = `14G`.
  - `ssh debian@10.150.0.173 df -h` (leader mgr03): `/dev/sda1 16G 15G 378M 98% /`.
  - mgr01 manager log, continuous since at least 12:58:21Z (every ~0.7s):
    `WARN dtfs_manager::server: Vote error: when Write Log(... term:114112,
    node_id:933575918632954229 ... index:2380332): ... No space left on device`.
- Expected: managers hold a small raft log; quorum = 3/3 voters writable. Raft
  log/snapshot storage compacted so it does not grow unbounded.
- Actual: mgr01 root fs 99% full, raft node has shut down and cannot append the
  log; mgr03 (the leader) is at 98% with 378M free. Quorum is degraded to 2/3
  (mgr02 + mgr03). Both surviving voters are nearly full — if mgr03 fills, the
  leader dies and the cluster loses quorum (read-only / unavailable, no write
  durability).
- Hypothesis: raft-log/snapshot dir on the 16G root partition is not being
  compacted (see Finding 5 — 14G of LOG.old + a 207MB MANIFEST). Disk filled,
  log append + snapshot write started failing, mgr01's raft node hit a fatal IO
  error and shut down. mgr03 provisioned identically and is on the same path.
- Suggested next step: triage as imminent quorum loss. Scope (a) reclaiming
  space on mgr01/mgr03 raft-log dirs (and check mgr02 — not measured this sweep,
  likely same provisioning), (b) why raft log compaction / snapshot retention is
  not running, (c) restarting mgr01's raft node once space is freed. Do NOT let a
  second manager fill.

## Finding 2: Confirmed data loss — all 184 files report chunk_count=0; data01 holds 0 chunks on disk

- Severity: critical
- Area: integrity / replication / anchor
- Evidence:
  - `GET /api/v1/files`: `count:184`, every entry `"chunk_count":0`,
    `"total_size":0` — including media files e.g.
    `/media/movies/Austin Powers in Goldmember (2002)/... .mkv` and the
    `/media/animes/Liar Liar/...mkv` season. `/api/v1/cluster/status`
    `used_capacity:56209408` (~56MB), `stats.logical_bytes:0`.
  - `ssh debian@10.150.0.174` (data01): `find /mnt/data01-warm/chunks -name '*.dat'
    | wc -l` = `0`; same for cold = `0`. `du -sh` = 39M warm / 2.8M cold (residue,
    not chunk files).
  - data01 `dtfs-data` scrub log shows the deletion window:
    `May 31 18:03 quick scrub on /mnt/data01-warm: checked=45 ...` then
    `Jun 01 00:04 quick scrub on /mnt/data01-warm: checked=0 ...`. Chunk count
    went 45 → 0 in that 6h window. (Sweep 3 had ~4441 chunks / 17.7GB on this
    disk; the bulk was already gone by May 31, the tail dropped to 0 on Jun 01.)
  - `/api/v1/migrations` count=0 — no repair in flight; nothing left to source.
- Expected: `default` volume `anchor={dc-a, cold}`, `mandatory_replicas.cold=1`,
  `replication.warm=2`. Each media file keeps its chunks with a cold anchor copy
  in dc-a plus warm copies.
- Actual: zero chunks remain on data01; file metadata for all 184 paths is
  stranded at chunk_count=0. The media is unreadable. This is the consummation of
  the data-loss risk flagged in sweep 3 (chunk `8cc014b2...` "no other replica to
  copy from"); audit now shows tiering `cache.demote ... result:noop_already_absent`
  for those same Austin Powers chunks (idx 50-54) — the engine is acting on chunks
  that are already gone.
- Hypothesis: the disk-UUID rotation bug (now fixed, Finding 6) orphaned the old
  chunk location records earlier in the campaign; GC orphan scrub then deleted the
  physical chunks (45 → 0 across May 31→Jun 01) while the FileMetadata entries
  survived with no chunk bindings. The UUID fix stops *new* orphaning but does not
  recover already-deleted data.
- Suggested next step: triage must treat this as realized data loss. Enumerate
  the affected media (all 184 entries under `default`), confirm none are
  recoverable from data02 (`used_capacity:8404992` ~8MB — almost certainly also
  empty of these chunks; verify via `/api/v1/files/inspect`), and decide
  re-ingest. Separately confirm GC was deleting on the basis of stale-UUID orphan
  classification, so the fix actually closes the deletion path.

## Finding 3: Leader mgr03 snapshot is empty/truncated — "Read Snapshot EOF"; migration state cannot persist

- Severity: high
- Area: raft
- Evidence: mgr03 (leader) manager log, continuous:
  `WARN dtfs_manager::server: Vote error: when Read Snapshot(None):
  std::io::error::Error: EOF while parsing a value at line 1 column 0`, and
  `WARN dtfs_manager::scheduler: Bug AB save_migration_state failed: when Read
  Snapshot(None): ... EOF while parsing a value at line 1 column 0 (may not be
  leader)`.
- Expected: the leader can read its own snapshot to serve vote/append and to
  install snapshots on followers; scheduler can persist migration state.
- Actual: snapshot read returns EOF at column 0 (file empty or truncated to zero
  bytes). Vote handling and migration-state save both fail on it.
- Hypothesis: a snapshot write was truncated when the disk hit 100% (Finding 1),
  leaving a 0-byte/partial snapshot. Tied to the storage exhaustion; freeing space
  alone may not repair an already-corrupt snapshot file — it may need to be
  regenerated.
- Suggested next step: after space is reclaimed, verify the snapshot file on
  mgr03 (`snapshot_index:2374794` per `/raft/state`) is valid; if truncated,
  scope regenerating it from the log or from a healthy peer. Confirm followers
  can still be brought current (last_log_index 2380332, snapshot 2374794 — gap is
  small, log-catchup should suffice if the log is intact).

## Finding 4: Data + client node liveness frozen (~17.5h data, ~4.9d client) but reported Healthy

- Severity: high
- Area: node
- Evidence: `/api/v1/nodes` — mgr `last_seen_ms:1780405072493`;
  data01 `1780342132839`, data02 `1780342136056` (~17.5h behind mgr),
  client01 `last_seen_ms:1779979398295` (~4.9d behind). All report
  `"health":"Healthy"`. Data daemons are up: `ssh ... systemctl is-active
  dtfs-data` = `active` on both data01 and data02; data01 scrub log shows
  activity through Jun 02.
- Expected: heartbeats land every few seconds; `last_seen_ms` tracks near-now;
  health reflects actual liveness.
- Actual: the daemons are alive and scrubbing locally, but their heartbeats have
  not updated the registry for ~17.5h (data) / ~4.9d (client), while health still
  shows Healthy — a stale-liveness projection masking the fault.
- Hypothesis: heartbeat (`UpdateNodeStatus`) is a raft write; with mgr01's raft
  node down and the leader's snapshot/disk degraded (Findings 1+3), those writes
  no longer commit, so `last_seen_ms` froze. This is the same heartbeat
  Raft-write-deferral surface noted in sweeps 1-3, now fully stalled by the
  storage fault rather than just lagging. The "Healthy" verdict not aging out on
  stale `last_seen` is its own projection bug.
- Suggested next step: once raft is healthy, confirm heartbeats resume and
  `last_seen_ms` advances. Separately scope making the health projection
  downgrade a node whose `last_seen` exceeds a liveness window instead of
  reporting Healthy indefinitely.

## Finding 5: Raft-log directory not compacting — 14G of LOG.old + 207MB MANIFEST (root cause of Finding 1)

- Severity: medium
- Area: raft
- Evidence: `ssh debian@10.150.0.171 ls -la /var/lib/dtfs/manager/raft-log`:
  multiple `LOG.old.*` files (single ones up to 55MB, 48MB, 19MB; dated May 28),
  `MANIFEST-2969210` = 207,081,860 bytes (Jun 1), plus the live `.sst` set;
  `du -sh raft-log` = 14G on a 16G partition.
- Expected: RocksDB LOG/MANIFEST rotation and raft log truncation keep the
  raft-log dir bounded well under the partition size.
- Actual: the dir has grown to 14G; old LOG files and a 207MB MANIFEST are not
  being reaped, and this is what filled the partition and triggered Finding 1.
- Hypothesis: log compaction / snapshot-driven truncation is either disabled,
  failing silently, or out-paced by the high raft term/election churn seen across
  the campaign (term 114112). Unbounded MANIFEST growth specifically suggests
  compaction is not running.
- Suggested next step: scope why raft log truncation + RocksDB LOG/MANIFEST
  rotation are not bounding the dir; consider a larger raft partition for the
  managers and/or a compaction trigger. This is the durable fix behind Finding 1.

## Summary

- critical: 2 (raft storage exhaustion / quorum degraded; confirmed data loss —
  184 files, 0 chunks on data01)
- high: 2 (leader snapshot truncated/EOF; node liveness frozen but Healthy)
- medium: 1 (raft-log dir not compacting — 14G/16G)
- low: 1 (tape replication knob on no-tape volumes)
- info / resolved: 1 (disk-UUID rotation fixed since sweep 3)

Single root cause links Findings 1, 3, 4, 5: the manager raft-log/snapshot
storage on a 16G root partition was never compacted (F5), filled to 99-100% (F1),
which truncated the leader's snapshot (F3) and stalled the raft writes that carry
heartbeats (F4). Finding 2 (data loss) is the now-materialized outcome of the
earlier UUID-rotation orphaning (F6, since fixed) + GC orphan deletion; it is
independent of the storage fault but equally terminal for the affected media.

Most urgent action for triage: reclaim raft-log space on mgr01 and mgr03 before a
second manager fills and quorum is lost — the cluster is one disk-full event away
from unavailability. Then assess data-loss recovery scope (re-ingest) and the
raft-log compaction fix so this does not recur.
