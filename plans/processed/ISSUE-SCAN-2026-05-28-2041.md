## Finding 1: Every chunk is single-replica on one node (critical)

- Severity: critical
- Area: replication
- Evidence: inspected all chunked files via `GET /api/v1/files/inspect?path=...`. Across 133 chunks (every chunked file in the volume): **replicas-per-chunk = {1: 133} (100% single-replica), and 100% live on `mini-data01`. Zero chunks have any copy on `mini-data02`.** Example: `/media/movies/Austin Powers in Goldmember (2002).../...mkv` — 55 chunks, all `node_ids=[9163562228154835649]` only.
- Expected: volume `default` declares `replication.warm=2` + `mandatory_replicas.cold=1` + `write_safety.min_replicas_before_ack=2`. Every chunk should hold ≥2 warm copies and ≥1 cold copy in dc-a.
- Actual: 1 copy per chunk, all on `mini-data01` warm. `mini-data02` (Healthy, empty) holds nothing; both cold disks are empty.
- Hypothesis: placement never distributed replicas to `mini-data02` and never created the mandatory cold copy. Either data02 joined after the data was written and back-fill never ran, or the placement/under-replication scheduler is only queuing cold-anchor tasks (see Finding 3) and not warm-distribution tasks. Single point of failure: if data01's disk dies, the entire 17.4 GB library is lost — and data01 already logged a corruption fault earlier today (Finding 6).
- Suggested next step: triage why the under-replication scheduler does not queue warm replication to data02 when `warm=2` is unmet; confirm whether data02 is a late joiner and whether back-fill is expected to cover pre-existing chunks.

## Finding 2: Anchor invariant violated — no chunk has its mandatory cold copy (critical)

- Severity: critical
- Area: anchor
- Evidence: same inspect sweep — 0 of 133 chunks have a cold-tier replica anywhere; both cold disks report ≈0 bytes used (`tier_breakdown` cold `used_bytes=11,513,856` ≈ 11 MB total). Volume anchor policy is `{dc-a, cold}`.
- Expected: every chunk keeps ≥1 mandatory replica on the dc-a cold tier (AGENTS.md §A.3.3/§A.3.4 anchor invariant).
- Actual: anchor coverage is effectively 0%. The mandatory cold copy is missing for the whole library.
- Hypothesis: cold-copy creation is permanently failing — see Finding 3.
- Suggested next step: tie to Finding 3; the anchor copies cannot be created until the source-resolution loop is fixed.

## Finding 3: Anchor-lag repair loops forever — "no healthy source replica" (high)

- Severity: high
- Area: migration
- Evidence: `GET /api/v1/migrations` → `count=299`, all `tier=cold`, status `{copying:106, failed:193}`. Error breakdown: **266× "no healthy source replica"**, 13× "chunk no longer exists (orphan task ...)". High-attempt tasks reach `attempts=6` with `source_node`/`target_node` both undefined. `GET /api/v1/audit?limit=300` is 100% this loop: 140× `anchor.lag_repair::scheduled` + 160× `migration.failed::no healthy source replica`, all within a 3.5-minute window (18:37:59 → 18:41:29Z). Sample looping chunk `2bb0810f...` (file `/media/animes/Liar Liar/.plexmatch`) appears in both the scheduled list and inspect shows its only replica is on data01.
- Expected: a chunk whose sole replica is warm on data01 should be copyable to the dc-a cold disk (same node, different tier — explicitly allowed per AGENTS.md §A.3.4 Bug BH: presence keyed by `(node_id, disk_id)`).
- Actual: repair schedules a cold copy, source resolution returns nothing healthy (source==target node rejected), task fails and is immediately re-queued — endless loop generating audit/migration spam.
- Hypothesis: the anchor-lag repair source resolver refuses to use a node as both source and target. When the chunk's only replica is on the same node that must host the cold anchor copy (the single dc-a data node here), it deadlocks on "no healthy source replica" instead of doing a local warm→cold copy. This is the BH co-location case on the apply/source-resolution side rather than the dedup side.
- Suggested next step: scope a fix so same-node cross-tier anchor copies resolve the local replica as a valid source (or place the cold copy on data02-cold as a fallback when dc-a cold can't be sourced). Connects to Findings 1 and 2.

## Finding 4: Warm tier saturated on data01 while data02 + all cold disks sit empty (high)

- Severity: high
- Area: disk / capacity
- Evidence: `GET /api/v1/nodes/9163562228154835649` — warm disk0 `used=19,866,927,104 / 20,957,446,144` (94.8%, 1091 MB free); cold disk1 `used=8,503,296` (≈0). `mini-data02` both disks ≈0. `tier_breakdown`: warm `used=19.88 GB`, cold `used=11.5 MB`.
- Expected: with warm overflow, placement should distribute to the second warm disk (data02) and/or spill to the cold tier; new writes should not abort while 60+ GB of cold/data02 capacity is free.
- Actual: warm data01 is nearly full and is the only disk holding data; matches the reported symptom that a client write aborts once data01 warm fills, with no fallback to cold.
- Hypothesis: same root as Findings 1/3 — placement is pinned to data01 warm and neither distributes across data02 nor spills to cold.
- Suggested next step: reproduce the aborted write on the lab and capture the data-node/manager log line for the allocation failure (SSH via jumpclient `dtfs-builder` 10.20.0.150 → `journalctl -u dtfs-manager` / `-u dtfs-data`); confirm whether the allocator considers cold/data02 candidates.
