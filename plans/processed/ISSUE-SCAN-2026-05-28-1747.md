  ```

  mini-data02 disk UUIDs: unchanged between sweeps.

  mini-data01 startup log at 15:15:45 (from `journalctl -u dtfs-data -n 40`):
  ```
  INFO dtfs_data::disk: Disk 0: /mnt/data01-warm (tier=warm, total=19GB, used=0GB)
  INFO dtfs_data::disk: Disk 1: /mnt/data01-cold (tier=cold, total=19GB, used=0GB)
  INFO dtfs_data::store: ChunkStore startup rescan complete chunks=28 bytes=109051904
  INFO dtfs_data: Registered with manager, assigned node_id: 9163562228154835649
  ```

  Cluster used_capacity: dropped from 2,112 MB (prior sweep) to 128 MB (current sweep). Delta: ~1,984 MB.

  `GET /api/v1/migrations` → `{"count":0,"tasks":[]}` — no re-replication queued.

  `GET /api/v1/integrity/faults` (both follower and leader) → `[]`.

- Expected: disk UUIDs are stable identifiers for a data node's physical disks. A UUID change indicates a disk was reformatted or replaced. After such an event, all chunk location records in Raft state that reference the old UUIDs become dangling — the chunks exist in the state machine but are no longer present on any disk. The under-replication scheduler must detect and queue repair tasks within one scheduler tick (30s). The `default` volume's `mandatory_replicas.cold=1` anchored to `dc-a` requires at least one cold copy on data01 (the dc-a data node); with only 2 cold chunks now present, almost all files' mandatory anchor copies are missing.
- Actual: both of data01's disk UUIDs changed while the cluster has 169 files. The disks were re-provisioned (formatted or physically replaced) between the prior sweep and this one. The ChunkStore startup rescan found only 28 chunks on the new disks — previously ~358 chunks were tracked. ~330 chunks worth of mandatory/cache replicas are now absent from data01. The state machine still retains location records for chunks on the old UUIDs (confirmed: no migration tasks queued, meaning the scheduler has not yet detected the missing locations, or is comparing against chunk records that still list the old disk as valid). The integrity feed is silent.
- Hypothesis: The disk UUIDs change means either (a) an operator reformatted/replaced the data01 disks as part of a test reset, or (b) data01 generates a new UUID on each service start (which would be a separate critical bug). Case (a) is a deliberate operation that bypassed the proper drain-and-replace procedure, leaving Raft state inconsistent. Case (b) would also apply to every data01 restart. Neither case has triggered automated re-replication. The anchor invariant (`dc-a/cold` mandatory copy) is likely violated for most of the 169 files.
- Suggested next step: Triage must (1) determine whether the disk change was intentional (operator test reset); (2) check whether the Raft state still holds chunk location records referencing the old disk UUIDs by comparing `GET /api/v1/chunks?node=<data01-id>` with the 28 chunks data01 actually has; (3) force-trigger the under-replication scheduler or wait one scheduler tick (30s) and re-check migrations; (4) run a deep scrub to surface all `orphan.in_state_missing` entries. Until this is confirmed safe, the anchor invariant for the default volume must be assumed violated.

  WARN dtfs_data: Heartbeat failed (2/3 before reconnect): ...
  WARN dtfs_data: Heartbeat failed (3/3 before reconnect): ...
  ERROR dtfs_data: Heartbeat failed 4 times, walking manager list for reconnect...
  INFO  dtfs_data: Reconnected to manager at http://10.150.0.172:9401
  ```

  From mini-data02 logs at 15:47:15-30 (same pattern):
  ```
  INFO dtfs_data: Reconnected to manager at http://10.150.0.172:9401
  ```

  Prior occurrence: both nodes at 10:14 (same pattern). Both nodes reconnecting to mgr02 (follower, never leader).

  Current `last_seen_ms` for data nodes: CURRENT (~2-3 seconds lag). This is because data01 re-registered at 15:16:56 via RegisterNode (restart), and data02 re-registered at some point after the prior sweep.

  Raft state: `current_leader=933575918632954229` (mini-mgr03 at `10.150.0.173:9401`). mgr02 (`10.150.0.172:9401`) is a follower.

- Expected: after heartbeat reconnect, data nodes should preferentially connect to the current leader so heartbeat Raft writes commit. If not connecting to the leader, the non-leader manager should proxy the write to the leader rather than deferring with "client should retry."
- Actual: both nodes reconnected to mgr02 (follower) at 15:47. The prior sweep showed mgr01 (also a follower) logging "Raft write deferred — not leader" for every heartbeat. mgr02 likely behaves identically. Future heartbeats from these nodes will fail to commit to Raft state, causing `last_seen_ms` to drift stale again. The failure is recurring: it happened at both 10:14 and 15:47 today. Each occurrence creates a ~3-5h liveness blindspot until the next restart or registration event. The reconnect logic walks the manager list sequentially — it does not select the leader.
- Hypothesis: the heartbeat connection target manager goes unavailable (network blip, restart), the data node walks the manager list and picks the next entry (which happens to be a non-leader), and subsequent heartbeats never commit because non-leader managers defer rather than forward.
- Suggested next step: Triage should scope (1) the non-leader Heartbeat RPC handler to forward to the leader instead of deferring, AND (2) the data node reconnect logic to use the leader address when a "not leader" response is received (same information is returned in the error: `has to forward request to: Some(...)`).
