## Finding 2: Self-quarantine immediately cleared by manager after integrity fault (Bug BF pattern)

- Severity: **high**
- Area: integrity, node
- Evidence:

  mini-data02, at `2026-05-28T09:28:20` (4 seconds after the integrity fault):
  ```
  WARN dtfs_data: Bug BF: manager cleared self-quarantine (operator unquarantine); re-enabling put_chunk
  ```

  mini-data01, at `2026-05-28T10:29:05` (1 second after the integrity fault):
  ```
  WARN dtfs_data: Bug BF: manager cleared self-quarantine (operator unquarantine); re-enabling put_chunk
  ```

- Expected: when a data node detects a corrupt chunk and self-quarantines, the quarantine should persist until the corruption is investigated or the chunk is repaired. Unquarantining within seconds of a detected fault re-enables `put_chunk` on a node whose integrity is in question.
- Actual: on both nodes, the manager issued an unquarantine within 1-5 seconds of the node self-quarantining in response to a BLAKE3 mismatch. Log prefix "Bug BF" on the data node's WARN line suggests this is the known BF code path.
- Hypothesis: the "operator unquarantine" path is being triggered automatically — either via an automated policy, the soak/test framework, or a bug in the manager that auto-clears any self-quarantine regardless of cause. This is not safe: the corrupt chunk remains on disk and the node is now fully accepting new writes.
- Suggested next step: Triage should determine who issued the unquarantine command (manager scheduler? test harness? automated policy?), and assess whether self-quarantine-on-integrity-fault should be resistant to automatic clearing.

## Finding 3: Data node heartbeats not committed to Raft state — node liveness timestamps ~4 hours stale

- Severity: **high**
- Area: node, raft
- Evidence:

  From `GET /api/v1/nodes`, as of 14:16 UTC:
  ```
  mini-data01: last_seen_ms=1779963255075  (~10:14 UTC today)
  mini-data02: last_seen_ms=1779963255473  (~10:14 UTC today)
  mini-mgr01:  last_seen_ms=1779977644311  (~14:16 UTC today, current)
  ```
  Lag: ~4 hours 2 minutes.

  From `journalctl` on mini-mgr01, as of 14:15 UTC (excerpt):
  ```
  DEBUG dtfs_manager::metadata: Heartbeat from node: 5195573662920911622
  WARN  dtfs_manager::metadata: Raft write deferred — not leader, client should retry
        error=has to forward request to: Some(933575918632954229),
        Some(DtfsNode { addr: "10.150.0.173:9401", hostname: "mini-mgr03" })
  ```
  This pattern repeats every 5 seconds continuously for node 5195573662920911622 (mini-data02).

  From mini-data01 logs at 10:14:35:
  ```
  ERROR dtfs_data: Heartbeat failed 4 times, walking manager list for reconnect...
  INFO  dtfs_data: Reconnected to manager at http://10.150.0.172:9401
  ```
  mini-data01 reconnected to mini-mgr02, also a non-leader.

  From mini-data02 logs at 10:14:20-30: 3 consecutive "tcp connect error" heartbeat failures, no reconnect log following.

- Expected: data node heartbeats commit to Raft state so `last_seen_ms` updates, enabling the health monitor to accurately track liveness (15s suspect, 30s down thresholds per prior analysis).
- Actual: after a TCP disconnection at ~10:14, both data nodes connected to non-leader managers (mgr01, mgr02). Non-leader managers receive heartbeat RPCs but respond "Raft write deferred — not leader, client should retry" without forwarding to the leader. Heartbeat Raft writes never commit. `last_seen_ms` is frozen at the last successful Raft-committed heartbeat (~10:14). The cluster API shows both data nodes as `health: "Healthy"` based on that stale state even though they have not had a liveness record committed in 4+ hours.
- Hypothesis: the non-leader Heartbeat RPC handler defers rather than forwarding to the leader. The data node heartbeat client retries on the same non-leader, not the leader. This creates a liveness blindspot: the cluster cannot detect if a data node actually goes down, and would not trigger re-replication.
- Suggested next step: Triage should scope a fix for the Heartbeat RPC handler on non-leader managers to proxy the write to the current leader (same pattern used by other forwarding paths in the codebase), and update the data node's reconnect logic to prefer the known leader when a "not leader" response is received.

## Finding 6: av-demo volume: `mandatory_replicas.tape=1` with no tape disks in cluster

- Severity: **medium**
- Area: volume
- Evidence:
  ```json
  GET /api/v1/volumes/av-demo →
  {
    "mandatory_replicas": { "cold": 1, "hot": 0, "tape": 1, "warm": 0 },
    "replication":        { "cold": 1, "hot": 0, "tape": 1, "warm": 0 }
  }
  ```
  All data nodes: disks are `tier: "warm"` or `tier: "cold"` only. No tape disks anywhere.

- Expected: `mandatory_replicas.tape` should be 0 on any volume deployed to a cluster without tape disks, or tape disks should exist to satisfy the constraint.
- Actual: `av-demo` has `mandatory_replicas.tape=1`. Currently harmless because `file_count=0`. The moment any file is written to av-demo, the under-replication scheduler will permanently fail to satisfy the tape mandatory constraint and queue failing migration tasks.
- Hypothesis: av-demo was configured for a topology that includes tape (perhaps copied from a production template) but was deployed to the Minicluster which has no tape tier.
- Suggested next step: Either remove the tape mandatory constraint on av-demo (set to 0), or ensure av-demo is never written to in the Minicluster environment.
