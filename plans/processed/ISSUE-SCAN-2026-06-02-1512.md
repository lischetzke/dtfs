## Finding 1: FUSE client reported `Down` while healthy — dtfs-client has no periodic heartbeat

- Severity: medium
- Area: node / client / liveness
- Evidence:
  - `GET /api/v1/nodes` — `mini-client01` (node_id `6841539694661734231`,
    client_ip `10.20.0.176`): `"health":"Down"`, `"role":"Client"`,
    `"grpc_addr":""`, `last_seen_ms:1780408984667`. Manager `last_seen_ms`
    ~`1780409134545` at query time → client ~150s stale and projected `Down`.
  - SSH `mini-client01`: the FUSE daemon is **alive and serving**:
    - `systemctl list-units "dtfs*"` → `dtfs-fuse@mnt-dtfs.service loaded active running`
      (note: `systemctl is-active dtfs-fuse` returns `inactive` — the real unit
      is the templated `dtfs-fuse@mnt-dtfs`, easy to mis-query).
    - `mount | grep dtfs` → `dtfs on /mnt/dtfs type fuse (rw,...,allow_other)`.
    - `pgrep -a dtfs` → `985898 /usr/local/bin/dtfs-fuse --config /etc/dtfs/fuse.toml --mountpoint /mnt/dtfs`; `etime` ~3:38 (restarted 14:03:04).
    - Startup log: `connected to manager pool count=3`, `mounting DTFS via fuse3 ... manager=10.20.0.171:9401`.
  - Client → manager reachability is fine: `</dev/tcp/10.20.0.{171,172,173}/9401`
    all `OPEN`.
  - Host is idle: `uptime` load average `0.00, 0.00, 0.00`; no FS activity in the
    FUSE log since the restart.
  - Code: `crates/dtfs-client/src/client.rs:1028` — client liveness is "Re-uses
    the existing `RegisterNode` RPC with `role="client"`". There is **no
    heartbeat loop** in `dtfs-fuse` / `dtfs-client`: the only
    `tokio::time::interval` in `dtfs-fuse` is the local-cache pruner
    (`local_cache.rs:349`). Contrast `crates/dtfs-data/src/main.rs:117` — data
    nodes run a dedicated heartbeat loop (~5s) that keeps `last_seen_ms` current.
  - Manager side is behaving correctly: `crates/dtfs-manager/src/api.rs:309`
    `effective_health` (Bug BP-3, deployed) downgrades a stale `Healthy` to
    `Down` once `last_seen_ms` age exceeds `raft.node_liveness_secs`.
- Expected: a mounted, serving FUSE client is reported reachable/healthy as long
  as the daemon is up and can reach a manager.
- Actual: an **idle** client emits no traffic after its startup `RegisterNode`,
  so `last_seen_ms` freezes; BP-3's liveness projection then correctly ages it to
  `Down`. The mount is fully healthy. The cluster reports the client offline
  purely because the client never refreshes its liveness.
- Hypothesis: the FUSE client was designed to register once (and re-register on
  RPC failure / on activity) rather than to heartbeat. Before BP-3 this surfaced
  as the long-standing "client `last_seen` frozen but Healthy" symptom (scans 1-4,
  e.g. 2026-05-28 F4/F7). BP-3 made the staleness visible by projecting `Down`,
  exposing the missing client-side heartbeat. Net effect: an idle-but-healthy
  client is indistinguishable from a genuinely dead one.
- Suggested next step: scope a periodic client heartbeat/keepalive — a light
  RPC (re-use `RegisterNode` role=client, or a dedicated client-ping) on an
  interval shorter than `raft.node_liveness_secs`, so an idle mount keeps its
  liveness fresh. Decide whether the client heartbeat should be a Raft write
  (durable but stalls when raft is degraded — the BP condition) or a
  leader-local liveness touch that does not require a committed log entry.
  Coordinate the interval with BP-3's `node_liveness_secs` default.

## Finding 2: `dtfs-fuse@mnt-dtfs` restart hit `/bin/fusermount3: No such file or directory` (203/EXEC)

- Severity: low
- Area: client / packaging
- Evidence: mini-client01 `journalctl -u dtfs-fuse@mnt-dtfs` around the 14:03:04
  restart:
  ```
  Jun 02 14:03:04 mini-client01 (ermount3)[985893]: dtfs-fuse@mnt-dtfs.service: Failed at step EXEC spawning /bin/fusermount3: No such file or directory
  Jun 02 14:03:04 mini-client01 systemd[1]: dtfs-fuse@mnt-dtfs.service: Control process exited, code=exited, status=203/EXEC
  ```
  The main daemon (pid 985898) nonetheless mounted successfully this cycle
  (`filesystem initialised`, `mounting DTFS via fuse3`).
- Expected: the unit's mount/unmount helper (`fusermount3`) resolves on PATH /
  at its real location (`/usr/bin/fusermount3` on this image).
- Actual: a control process referenced `/bin/fusermount3`, which does not exist;
  the step failed `203/EXEC`. The mount worked anyway here, but a clean
  stop/unmount that relies on `fusermount3` at `/bin` will fail.
- Hypothesis: the systemd unit (or an ExecStop/ExecStopPost) hardcodes
  `/bin/fusermount3` while the binary lives at `/usr/bin/fusermount3`; or the
  package providing `fusermount3` is not installed where the unit expects.
- Suggested next step: low priority — fix the unit to locate `fusermount3` via
  PATH (or correct the absolute path) in the deploy/systemd surface; confirm
  `fuse3` userspace tools are installed on the client image.

## Summary

- medium: 1 (idle FUSE client reported `Down` — dtfs-client has no periodic
  heartbeat; BP-3 liveness projection correctly ages a never-refreshing client
  to `Down`)
- low: 1 (`/bin/fusermount3` 203/EXEC on unit restart; mount succeeded anyway)

The client is not actually offline: the `dtfs-fuse@mnt-dtfs` daemon is up,
`/mnt/dtfs` is mounted, and all three managers are reachable on 9401. The
manager reports it `Down` only because the client never refreshes `last_seen_ms`
after startup and the BP-3 liveness window elapsed on an idle mount. The durable
fix is a client-side heartbeat; the fusermount3 path error is a separate,
low-severity packaging nit.
